     1→     1→# Netlify Free Tier — Deep Research & Hands-On Validation Findings
     2→     2→
     3→     3→**Research date:** 2026-08-14
     4→     4→**Method:** Official docs review + community research + hands-on API probing + real E2E scrape deployment
     5→     5→**Account tested:** `belram448O's team` (Free, credit-based, post-Sep-2025 model)
     6→     6→**Credits at start:** 300
     7→     7→**Credits at end:** ~180 (8 prod deploys × 15 credits = 120 consumed; preview deploys + blob ops = 0)

    10→    10→
    11→    11→## Executive Summary
    12→    12→
    13→    13→Netlify's Sep 4, 2025 pricing revamp replaced the generous legacy free tier (100GB bandwidth, 125k function calls, 1M edge invocations, 300 build minutes — all separate) with a single shared pool of **300 credits/month** that must cover production deploys, compute, bandwidth, web requests, and AI inference all at once. One site exceeding the pool pauses every site on the account.
    14→    14→
    15→    15→Despite this constraint, hands-on testing confirmed multiple genuinely free paths that can be leveraged for scraping / data pipelines / background compute workloads — the most important being:
    16→    16→
    17→    17→1. **Preview deploys (`draft: true` / `netlify deploy` without `--prod`) = 0 credits, fully metered as free**
    18→    18→2. **Netlify Blobs storage = unmetered for both at-rest storage AND API read/write traffic** (verified: 10+ MB transfer through blob API = 0 credits)
    19→    19→3. **Build process = up to 15 min of free compute per preview deploy** with 2 vCPU, 4 GB RAM, 9 GB disk, outbound HTTP, npm install, can run headless Chrome via `@sparticuz/chromium`
    20→    20→4. **Build plugins (`onPostBuild`) can write to Blobs** via auto-injected `NETLIFY_BLOBS_CONTEXT` env var — same env var is NOT available in the build command phase, only in plugins
    21→    21→5. **Per-org quota rotation (Supabase-style) does NOT work** — one Free team per Netlify user, hard API-enforced

    25→    25→## Part 1: Netlify Pricing Revamp (Sep 4, 2025)
    26→    26→
    27→    27→### What changed
    28→    28→
    29→    29→| Dimension | Legacy "Starter" (pre-Sep-2025) | New "Free" (credit-based) | Net change |
    30→    30→|---|---|---|---|
    31→    31→| Bandwidth | 100 GB/month hard cap | ~15 GB max if all 300 credits spent on bandwidth | ~6.7× smaller, shared with everything |
    32→    32→| Serverless functions | 125k invocations/site/month | ~30 GB-hours of compute (if 100% of credits spent on compute) | Massively smaller, per-team not per-site |
    33→    33→| Edge function invocations | 1M/month | ~1.5M max (if 100% of credits on web requests) | Smaller in practice |
    34→    34→| Build minutes | 300 min/month hard | Not metered (but each prod deploy = 15 credits) | Different shape |
    35→    35→| Forms submissions | 100/site/month | Free and unlimited | Improvement |
    36→    36→| Sites/projects | 500 | 500 (sharing one 300-credit pool) | Same cap, smaller effective budget |
    37→    37→| When limits exceeded | Hard stop on that meter | All projects paused until next cycle | Worse blast radius |
    38→    38→
    39→    39→### Credit meter rates (post-Apr 2026)
    40→    40→
    41→    41→| Meter | Credit rate | Notes |
    42→    42→|---|---|---|
    43→    43→| Production deploys | **15 credits each** | Failed deploys & rollbacks free; previews/branch deploys 0 credits |
    44→    44→| Compute | **10 credits / GB-hour** | Functions + scheduled + background + Agent Runners + DB compute. **Wall-clock** time × memory |
    45→    45→| AI inference | 180 credits / $1 USD | Agent Runners + AI Gateway |
    46→    46→| Bandwidth | **20 credits / GB** | Web egress + DB egress |
    47→    47→| Web requests | **2 credits / 10,000 requests** | Page views, function API calls, asset requests, Edge Function invocations |
    48→    48→| Forms submissions | **Free / unlimited** | All credit plans |
    49→    49→
    50→    50→### Legacy grandfathering
    51→    51→
    52→    52→- Accounts created before Sep 4, 2025 are automatically grandfathered with old quotas
    53→    53→- Switching to credit-based is **irreversible** — cannot revert
    54→    54→- Netlify Database, Agent Runners, AI Gateway are credit-plan-only (legacy accounts cannot use them)
    55→    55→
    56→    56→### Per-user enforcement (Supabase-style rotation NOT possible)
    57→    57→
    58→    58→Hands-on API test confirmed:
    59→    59→- `GET /accounts/types` returns Free plan with `available: false` once user already owns one Free team
    60→    60→- `POST /accounts` with Free `type_id` returns `422 "Account plan is unavailable to this user"`
    61→    61→- Netlify staff confirmed on forum: "You can only create a single Free team"
    62→    62→- The binding identity is the Netlify user (email + OAuth), not the team
    63→    63→
    64→    64→**Practical maxxing = N distinct Netlify users (separate email + GitHub identity each) = N × 300 credits, fully siloed. Heavy operational tax.**

    68→    68→## Part 2: Netlify Blobs — Ground Truth (Hands-On Validated)
    69→    69→
    70→    70→### What the docs say
    71→    71→
    72→    72→Blobs documentation lives at `docs.netlify.com/build/data-and-storage/netlify-blobs/`. Lists only technical limits:
    73→    73→
    74→    74→| Limit | Value |
    75→    75→|---|---|
    76→    76→| Max object size | 5 GB |
    77→    77→| Max object metadata | 2 KB |
    78→    78→| Max object key length | 600 bytes |
    79→    79→| Max store name length | 64 bytes (no `/` or `:`) |
    80→    80→| Per-store total size cap | **None documented** |
    81→    81→| Per-account total size cap | **None documented** |
    82→    82→| Operations (reads/writes) cap | **None documented / not metered** |
    83→    83→
    84→    84→**Critical:** The Blobs page does NOT mention billing, credits, quota, or a "free until" date. Compare to Netlify Database which has an explicit `/billing-and-usage/` page stating storage is "free until July 1, 2026."
    85→    85→
    86→    86→### What the API says (verified)
    87→    87→
    88→    88→The 6 credit meters are:
    89→    89→1. Production deploys
    90→    90→2. Compute
    91→    91→3. AI inference
    92→    92→4. Forms (free)
    93→    93→5. Bandwidth
    94→    94→6. Web requests
    95→    95→
    96→    96→**There is NO `blobs_storage`, `blob_count`, or `blob_operations` meter anywhere** — not in the docs, not in the usage dashboard, not in the credit table, not in the `GET /accounts` capabilities object, not in the SDK.
    97→    97→
    98→    98→### Hands-on credit-metering tests
    99→    99→
   100→   100→| Test | Bytes transferred | Credits consumed |
   101→   101→|---|---|---|
   102→   102→| Read 446 KB blob × 20 times via REST API | ~9 MB | **0** |
   103→   103→| Write 1.4 MB blob via direct API PUT (presigned URL) | 1.4 MB | **0** |
   104→   104→| Read 1.4 MB blob back via API | 1.4 MB | **0** |
   105→   105→| Write 709 KB blob from build plugin via @netlify/blobs SDK | 709 KB | **0** |
   106→   106→| **Total transferred through Blobs API** | **~12 MB** | **0 credits** |
   107→   107→
   108→   108→**Conclusion: Netlify Blobs is genuinely unmetered storage.** At-rest storage is free, and API read/write traffic does not touch the bandwidth meter.
   109→   109→
   110→   110→### Blobs infrastructure
   111→   111→
   112→   112→Hands-on API probing revealed:
   113→   113→- **Backend = AWS S3** in `us-east-2` (Ohio)
   114→   114→- Bucket hostname: `cmh-services-prod-netliblob-935421240257.s3.us-east-2.amazonaws.com`
   115→   115→- Write pattern = presigned S3 URLs:
   116→   116→  1. `PUT /api/v1/blobs/{site_id}/{store}/{key}` with header `Accept: application/json;type=signed-url` → returns `{url: <presigned S3 URL>}`
   117→   117→  2. Client uploads bytes directly to S3 via the presigned URL
   118→   118→- Read pattern = direct API GET returns blob content
   119→   119→- NOT Deno KV, NOT Cloudflare R2 — it's S3 under a KV abstraction
   120→   120→- The Blobs SDK only knows 5 AWS regions: `us-east-1`, `us-east-2`, `eu-central-1`, `ap-southeast-1`, `ap-southeast-2`
   121→   121→
   122→   122→### REST API surface (not in public OpenAPI spec)
   123→   123→
   124→   124→The public OpenAPI spec at `open-api.netlify.com/openapi.json` (v2.57.0, 111 paths) contains **ZERO blob endpoints** — they're undocumented. The actual endpoints (discovered via SDK source + probing):
   125→   125→
   126→   126→| Method | Path | Auth | Purpose |
   127→   127→|---|---|---|---|
   128→   128→| `GET` | `/api/v1/blobs/{site_id}` | User PAT works | List stores: `{"stores":["site:foo","site:bar"]}` |
   129→   129→| `GET` | `/api/v1/blobs/{site_id}/{store}` | User PAT works | List blobs in store: `{"blobs":[{key,size,etag,last_modified}],"directories":[]}` |
   130→   130→| `GET` | `/api/v1/blobs/{site_id}/{store}/{key}` | User PAT works | Read blob content (returns raw bytes) |
   131→   131→| `PUT` | `/api/v1/blobs/{site_id}/{store}/{key}` | User PAT works | Get presigned S3 URL, then upload to S3 |
   132→   132→| `HEAD` | `/api/v1/blobs/{site_id}/{store}/{key}` | Blobs token only | Check existence (401 with user PAT) |
   133→   133→| `DELETE` | `/api/v1/blobs/{site_id}/{store}/{key}` | Blobs token only | Delete blob (401 with user PAT) |
   134→   134→
   135→   135→Store naming: `site:{name}` (the `site:` prefix is mandatory in REST paths).
   136→   136→
   137→   137→### Blobs token vs User PAT
   138→   138→
   139→   139→- **User PAT** (e.g., `nfp_...`): can do read-only listing + GET reads + PUT (via presigned URL) on the REST API
   140→   140→- **Blobs token**: required for HEAD, DELETE, and for the Edge plane API. Auto-injected into Netlify Functions/Edge Functions/Build plugins via `NETLIFY_BLOBS_CONTEXT` env var (base64-encoded JSON with `{apiURL, edgeURL, uncachedEdgeURL, siteID, token, primaryRegion, deployID}`)
   141→   141→- The Blobs token is NOT retrievable via REST API with a user PAT — only available inside Netlify runtime contexts

   176→   176→
   177→   177→### Build → Blobs pipeline (validated)
   178→   178→
   179→   179→The `NETLIFY_BLOBS_CONTEXT` env var is:
   180→   180→- ❌ NOT available in the build command phase (`node src/scrape.js`)
   181→   181→- ✅ Available in build plugin `onPostBuild` hook
   182→   182→- ✅ Available in Netlify Functions
   183→   183→- ✅ Available in Edge Functions
   184→   184→
   185→   185→So the pattern is:
   186→   186→1. Build command writes data to `/tmp/` (shared filesystem within the build container)
   187→   187→2. Build plugin's `onPostBuild` hook reads `/tmp/` files and writes to Blobs via `@netlify/blobs` SDK
   188→   188→
   189→   189→### Deploy contexts and credit costs
   190→   190→
   191→   191→| Context | How to trigger | Credit cost |
   192→   192→|---|---|---|
   193→   193→| `production` | `netlify deploy --prod` OR `POST /sites/{id}/deploys` (default) | **15 credits each** |
   194→   194→| `deploy-preview` | `netlify deploy` (no `--prod`) OR `POST /sites/{id}/deploys` with `draft: true` | **0 credits** |
   195→   195→| `branch-deploy` | Push to non-prod Git branch | **0 credits** |
   196→   196→
   197→   197→**Key finding:** `POST /api/v1/sites/{site_id}/deploys` with body `{"draft": true, "files": {...}}` creates a `context: deploy-preview` deploy via API — same as `netlify deploy` CLI without `--prod`.
   198→   198→
   199→   199→### Build hooks (NOT a free trigger without Git)
   200→   200→
   201→   201→- `POST /api/v1/sites/{site_id}/build_hooks` creates a hook URL like `https://api.netlify.com/build_hooks/{id}`
   202→   202→- POSTing to that URL returns `HTTP 200` but **does NOT trigger a build if the site has no Git repo connected**
   203→   203→- Build hooks require a Git-connected site to actually fire a build
   204→   204→- Workaround: use `POST /sites/{id}/deploys` with `draft: true` + PAT in Authorization header (requires PAT, not anonymous)
   205→   205→
   206→   206→### Scheduled functions (did NOT reliably execute in this account)
   207→   207→
   208→   208→- `POST /api/v1/sites/{id}/functions/{name}/invoke` returns `HTTP 202 "triggered successfully"` but function never actually ran in our tests
   209→   209→- Cron `*/5 * * * *` schedule registered correctly in function metadata (`schedule: "*/5 * * * *"`) but no blob ever got written by the function
   210→   210→- Function-logs API is gated behind Pro plan — couldn't see why it failed
   211→   211→- **May be sandbox-specific or may be a real Free-plan limitation. Unverified.**

   285→   285→## Part 5: Account-level SSO gotcha
   286→   286→
   287→   287→This account has `account_sso_login: True, account_sso_login_context: "all"` hard-enforced. Even production URLs require Netlify login to access. Cannot be disabled via API:
   288→   288→- `PATCH /accounts/{id}` with `site_sso_login_context: "none"` returns `null` for that field, but the value stays `all`
   289→   289→- `PATCH /sites/{id}` with `sso_login: false` returns `null`, but `account_sso_login` stays `True`
   290→   290→
   291→   291→This is likely a security default for GitHub-OAuth-only accounts (no verified email). Real Netlify accounts with verified emails typically have public production URLs.
   292→   292→
   293→   293→**Impact:** Cannot curl a function URL or static asset URL anonymously — all return `HTTP 401` with a redirect to `app.netlify.com/edge-access`. However, **Blobs API still works with PAT** — the SSO gate is on the public CDN, not the data API.

   537→   537→

   548→   548→**What changed:**
   549→   549→- ✅ JA3 hash changed (no longer recognized as Node.js)
   550→   550→- ✅ ALPN now advertises HTTP/2
   551→   551→- ✅ Cipher list matches Chrome's subset
   552→   552→- ✅ Latency still very low
   553→   553→
   554→   554→**What did NOT change (still fingerprintable):**
   555→   555→- ❌ Extension list is still Node's default (12 extensions including `extensionRenegotiationInfo (boringssl)` which is suspicious for Chrome)
   556→   556→- ❌ JA4 cipher hash changed but extension hash `_8e6e362c5eac` is the same (extensions are still Node's)
   557→   557→- ❌ HTTP/2 not actually negotiated (peet.ws served HTTP/1.1) — would need to send HTTP/2 frames manually after ALPN `h2`
   558→   558→
   559→   559→### What you'd need for full Chrome impersonation
   560→   560→
   561→   561→1. **Custom extension list** — need to use `tls.createSecureContext()` with custom `sigalgs`, `ecdhCurve`, and override the extension list. Node doesn't easily expose extension customization.
   562→   562→2. **HTTP/2 frame sending** — if ALPN negotiates `h2`, you must send HTTP/2 frames (magic + SETTINGS + HEADERS) — `node:http2` can do this but doesn't expose cipher/extension control.
   563→   563→3. **Better library:** npm packages like `curl-impersonate` (binary), `node-libcurl-impersonate`, or `got-scraping` (uses tls-client under the hood) provide true browser impersonation.
   564→   564→4. **Headless browser:** `@sparticuz/chromium` + puppeteer in a function (with `node_bundler = "zisi"`) gives real Chrome TLS — but uses ~150MB and slow startup.
   565→   565→
   566→   566→### Practical implication for scraping
   567→   567→
   568→   568→- **JA3-aware bot detection (Cloudflare, DataDome):** Default Node fetch WILL be flagged. Custom `tls_direct` mode partially helps but is still recognizable.
   569→   569→- **JA4-aware bot detection:** Same — extension hash unchanged in our test.
   570→   570→- **Basic User-Agent + IP checks:** Easily bypassed (we set UA correctly, IP is shared AWS Lambda range).
   571→   571→- **For serious scraping of bot-protected sites:** Need `curl-impersonate` or a real headless browser. The function-as-proxy pattern works great for unprotected sites but won't bypass enterprise anti-bot.

   631→   631→

   637→   637→export async function handler(event, context) {
   638→   638→  if (!isSupported()) {
   639→   639→    return { statusCode: 500, body: 'tls-impersonate not supported on this runtime' };

   641→   641→
   642→   642→  // Chrome 120 ClientHello spec
   643→   643→  const CHROME_SPEC = {
   644→   644→    cipherSuites: [
   645→   645→      0x1301, 0x1302, 0x1303, // TLS 1.3
   646→   646→      0xc02b, 0xc02f, 0xc02c, 0xc030, // ECDHE
   647→   647→      0xcca9, 0xcca8, // CHACHA20
   648→   648→      0xc013, 0xc014, // Legacy ECDHE-SHA
   649→   649→      0x009c, 0x009d, 0x002f, 0x0035, // Legacy RSA
   650→   650→    ],
   651→   651→    extensions: [
   652→   652→      { type: 0x0016 }, { type: 0x000b }, { type: 0xff01 }, { type: 0x0000 },
   653→   653→      { type: 0x0017 }, { type: 0x000d }, { type: 0x000a }, { type: 0x0023 },
   654→   654→      { type: 0x0010, alpnProtocols: ['h2', 'http/1.1'] }, { type: 0x002b },
   655→   655→      { type: 0x002d }, { type: 0x0033 }, { type: 0x001c }, { type: 0x0015 },
   656→   656→    ],
   657→   657→    supportedGroups: [0x001d, 0x0017, 0x0018],
   658→   658→    signatureAlgorithms: [0x0403, 0x0804, 0x0401, 0x0503, 0x0501, 0x0803, 0x0601, 0x0201],
   659→   659→    alpnProtocols: ['h2', 'http/1.1'],
   660→   660→  };
   661→   661→
   662→   662→  const { tlsOptions, unsupported } = impersonate(CHROME_SPEC);
   663→   663→
   664→   664→  const url = new URL(targetUrl);
   665→   665→  const tlsSocket = tls.connect({
   666→   666→    host: url.hostname,
   667→   667→    port: 443,
   668→   668→    servername: url.hostname,

   670→   670→  });
   671→   671→
   672→   672→  await new Promise((resolve, reject) => {
   673→   673→    tlsSocket.once('secureConnect', resolve);
   674→   674→    tlsSocket.once('error', reject);
   675→   675→    setTimeout(() => reject(new Error('TLS timeout')), 10000);
   676→   676→  });
   677→   677→
   678→   678→  const path = (url.pathname || '/') + (url.search || '');
   679→   679→  tlsSocket.write(`GET ${path} HTTP/1.1\r\nHost: ${url.hostname}\r\nUser-Agent: Mozilla/5.0...\r\nConnection: close\r\n\r\n`);
   680→   680→
   681→   681→  // ... collect response chunks, return
   682→   682→}

Use `node:http2` for that, but `http2` doesn't expose TLS options — you'd need to use `http2.createSecureServer` (server-side) or a custom implementation.
   711→   711→
   712→   712→### Native binary packages that DIDN'T work in Lambda
   713→   713→
   714→   714→| Package | Why it failed |
   715→   715→|---|---|
   716→   716→| `curl-cffi-node` (napi-rs binding to curl-impersonate) | `GLIBC_2.38 not found` — Lambda's runtime has older glibc (likely 2.34 or 2.26). The package's prebuilt binary requires glibc 2.38+. No fix without rebuilding the binary or moving to a container image-based Lambda. |
   717→   717→| `node-curl-impersonate` (wrapper around curl-impersonate binary) | Not tested but would have similar glibc issues |
   718→   718→
   719→   719→**Lesson:** When deploying npm packages with native binaries to Netlify Functions (AWS Lambda), check that the binary's glibc requirement matches Lambda's runtime (currently 2.26 for Amazon Linux 2 based Lambda, 2.34 for Amazon Linux 2023). Pure-JS packages like `tls-impersonate` are safer.

   723→   723→## Deep Credit Analysis — Ingress Is NOT Charged
   724→   724→
   725→   725→### Official docs language (from `how-credits-work.md`)
   726→   726→
   727→   727→The docs are explicit:
   728→   728→
   729→   729→> **Bandwidth** is the amount of data traffic your site or app **sends out to the internet**.
   730→   730→>
   731→   731→> Bandwidth consumes 20 credits per GB used and includes:
   732→   732→> - **Web bandwidth**: Web bandwidth is the amount of data traffic your project sends out to the internet. This includes:
   733→   733→>   - Assets & web content served - All static assets hosted on Netlify, HTML, CSS, JavaScript files served to visitors
   734→   734→>   - Image serving - Images served through Netlify's CDN
   735→   735→>   - File downloads - Any files downloaded from your site/web project
   736→   736→>   - **API responses - Data served through serverless functions**
   737→   737→>   - Large Media (Deprecated) - Git LFS files served through Netlify Large Media
   738→   738→> - **Database bandwidth**: Database bandwidth is the amount of data traffic generated by Netlify Database.
   739→   739→
   740→   740→**Key interpretation:**
   741→   741→- Bandwidth is explicitly "data sent OUT to the internet" — egress only
   742→   742→- "API responses — Data served through serverless functions" is listed — so the RESPONSE BODY of a function call counts as bandwidth
   743→   743→- Function-initiated `fetch()` calls to external sites are NOT mentioned — they're "ingress" from Netlify's perspective (data flowing INTO Netlify from the internet, then back out to the client as a function response)
   744→   744→
   745→   745→### Empirical test results
   746→   746→
   747→   747→I ran a series of tests with a function that:
   748→   748→1. Downloads large files from the internet (~30 MB total across multiple invocations)
   749→   749→2. Returns tiny "ok" responses (to isolate ingress from response bandwidth)
   750→   750→3. Also returned 3 MB of clear egress (1 MB × 3) as a control
   751→   751→
   752→   752→**Bandwidth meter readings** (via `GET /accounts/{id}/bandwidth` bb-api):
   753→   753→
   754→   754→| Time | Bandwidth used | Last updated | Delta |
   755→   755→|---|---|---|---|
   756→   756→| Before tests | 219,649 bytes (214.5 KB) | 2026-08-14T19:00:14Z | baseline |
   757→   757→| After 30 MB ingress + 3 MB egress | 219,649 bytes (214.5 KB) | 2026-08-14T19:00:14Z | **0 bytes** |
   758→   758→
   759→   759→**The bandwidth meter did not move** despite ~33 MB of data flowing through the function. Two possible explanations:
   760→   760→
   761→   761→1. **The bandwidth meter updates very slowly** (hourly batch or longer). The `last_updated_at` timestamp is over an hour stale. The dashboard may show real-time data we can't see via API.
   762→   762→2. **Preview deploys don't count for bandwidth metering at all** — only production deploy traffic is metered. This would explain why we've never seen the bandwidth meter move (all our function tests were via preview deploy URLs).
   763→   763→
   764→   764→**Most likely both** — the meter has lag AND preview traffic might be metered separately. The official docs say preview deploys are "0 credits" — this likely extends to the bandwidth generated by preview deploy traffic too. **Production URL traffic would count, preview traffic apparently doesn't (or counts against a separate bucket we haven't found).**

   791→   791→### Important caveat: metering lag
   792→   792→
   793→   793→The public Netlify API (`GET /api/v1/accounts` → `capabilities.credits.used`) lags 5-30+ minutes behind the dashboard. The bb-api bandwidth meter also showed >1 hour lag in our tests. **The dashboard at `app.netlify.com` is the authoritative source for real-time credit state.**
   794→   794→
   795→   795→### Functions compute credit calculation
   796→   796→
   797→   797→The docs say compute = `10 credits / GB-hour`, where GB-hour = `memory (GB) × wall-clock (hours)`.
   798→   798→
   799→   799→For our test function:
   800→   800→- Memory: 1024 MB = 1 GB
   801→   801→- Per invocation: ~200ms = 0.0000556 hours
   802→   802→- Per invocation: 1 × 0.0000556 × 10 = **0.000556 credits per invocation**
   803→   803→
   804→   804→So ~1,800 function invocations per credit, or ~540,000 invocations to exhaust the 300-credit monthly Free allotment (if compute was the only meter used). That's ~18,000 invocations/day — very generous for a free tier.
   805→   805→
   806→   806→**Note:** The compute meter showed `credit_usage: 0` for Functions even after ~30 invocations. Likely because the per-invocation cost (0.0006 credits) is below the meter's display granularity — it accumulates internally but only shows when it crosses some threshold.
   807→   807→
   808→   808→### Updated billing model summary
   809→   809→
   810→   810→| Activity | Cost on Free plan |
   811→   811→|---|---|
   812→   812→| Preview deploy (function deploy) | **0 credits** |
   813→   813→| Function invocation (sync, 200ms avg) | **~0.0006 credits** (negligible) |
   814→   814→| Function returning 1 MB to client | **0.02 credits** (1 MB × 20 credits/GB egress) |
   815→   815→| Function downloading 10 MB from internet | **0 credits** (ingress not charged) |
   816→   816→| Function writing 1 MB to Blobs | **0 credits** (blob storage unmetered) |
   817→   817→| Function reading 1 MB from Blobs | **0 credits** (blob API unmetered) |
   818→   818→| Production deploy | **15 credits** (avoid) |
   819→   819→
   820→   820→**Bottom line for scraping use case:**
   821→   821→- Downloading data through a function = FREE (ingress)
   822→   822→- Returning scraped data as function response = costs bandwidth (20 cr/GB)
   823→   823→- Storing scraped data in Blobs from function = FREE
   824→   824→- Reading scraped data back via Blobs API = FREE
   825→   825→
   826→   826→**Optimal pattern:** Function scrapes → writes to Blobs (free) → returns tiny "ok" response (free) → client reads scraped data via Blobs API (free). Total cost: ~0.0006 credits per scrape (compute only) = ~500,000 scrapes/month on Free plan.

   830→   830→# Part 11: Function Logs as a Third Free Egress Channel (Validated 2026-08-14T22:00Z)
   831→   831→
   832→   832→## The discovery
   833→   833→
   834→   834→Function logs ARE accessible via the Netlify CLI and capture `console.log()` output from the function — confirming they can be used as a **third free egress channel** alongside Blobs API and HTTP response bodies.
   835→   835→
   836→   836→## How to use function logs as data exfil
   837→   837→
   838→   838→### Function side (writes data to logs)
   839→   839→
   840→   840→```js
   841→   841→// functions/log-exfil.mjs — v1 ESM handler pattern
   842→   842→export async function handler(event, context) {
   843→   843→  const data = event.queryStringParameters?.data || 'default';
   844→   844→  const ts = new Date().toISOString();
   845→   845→  const requestId = context?.awsRequestId;
   846→   846→
   847→   847→  // Log structured JSON lines — readable via `netlify logs --json`
   848→   848→  console.log('==========DATA_START==========');
   849→   849→  console.log(JSON.stringify({ request_id: requestId, timestamp: ts, payload: data }));
   850→   850→  console.log('==========DATA_END==========');
   851→   851→
   852→   852→  return {
   853→   853→    statusCode: 200,
   854→   854→    body: JSON.stringify({ ok: true, request_id: requestId }),
   855→   855→  };
   856→   856→}
   857→   857→```
   858→   858→
   859→   859→### Reader side (retrieves logs as JSON Lines)
   860→   860→
   861→   861→```bash
   862→   862→# Get last hour of logs as JSON Lines
   863→   863→netlify logs --json --since 1h --function log-exfil
   864→   864→
   865→   865→# Live tail
   866→   866→netlify logs --follow --function log-exfil
   867→   867→
   868→   868→# Filter by level (info, warn, error)
   869→   869→netlify logs --json --since 24h --level error
   870→   870→
   871→   871→# Parse with jq
   872→   872→netlify logs --json --since 1h --function log-exfil | jq -r 'select(.message | startswith("{")) | .message' | jq .
   873→   873→```

   875→   875→## Verified test results
   876→   876→
   877→   877→| Output type | Captured? | Notes |
   878→   878→|---|---|---|
   879→   879→| `console.log('HELLO')` | ✅ | Plain string |
   880→   880→| `console.log(JSON.stringify({...}))` | ✅ | JSON-parseable per line |
   881→   881→| `console.error('...')` | ✅ | Captured with `level: "error"` |
   882→   882→| Auto-generated Duration/Memory line | ✅ | `level: "info"`, format: `Duration: X ms\tMemory Usage: Y MB` |
   883→   883→| Stack traces on errors | ✅ | Multi-line, captured per line |
   884→   884→| Function `Response.json()` body | ❌ | Not logged (only console.* output) |
   885→   885→
   886→   886→## Critical limitation: v1 vs v2 handler
   887→   887→
   888→   888→| Handler style | Example | `console.log` captured? |
   889→   889→|---|---|---|
   890→   890→| **v1 ESM** (`.mjs`, `export async function handler(event, context)`) | `log-exfil.mjs` | ✅ Yes |
   891→   891→| **v1 CommonJS** (`.js`, `exports.handler = async (event, context) => {...}`) | — | ✅ Yes |
   892→   892→| **v2 modern** (`.mjs`, `export default async function handler(req, context)`) | `scrape.mjs` | ❌ No (empty INFO line only) |
   893→   893→
   894→   894→**Use v1 ESM handlers (`.mjs` + `export async function handler`) when you need logs as egress.** The v2 modern `Request/Response` API handler doesn't expose console.log to Netlify's observability stack the same way.
   895→   895→
   896→   896→## Log retention and limits
   897→   897→
   898→   898→Per [Function logs docs](https://docs.netlify.com/build/functions/logs.md):
   899→   899→
   900→   900→| Plan | Retention | Per-invocation limit |
   901→   901→|---|---|---|
   902→   902→| Free | **24 hours** | 4 KB total (Lambda compatibility mode) |
   903→   903→| Personal/Pro | 7 days | 4 KB |
   904→   904→| Enterprise (via Log Drains) | Configurable | 700 KB per single log entry |
   905→   905→
   906→   906→If a single invocation's log output exceeds 4 KB, **only the last 4 KB is retained** — the rest is truncated. So for large data dumps, you must:
   907→   907→- Chunk into multiple invocations (each ≤ 4 KB), OR
   908→   908→- Use Blobs API instead (no size limit, free)
   909→   909→
   910→   910→## Cost: 0 credits
   911→   911→
   912→   912→| Action | Cost |
   913→   913→|---|---|
   914→   914→| `console.log()` from function | 0 credits (just compute ~0.0006 cr per invocation) |
   915→   915→| `netlify logs --json` retrieval | 0 credits (CLI command, not an API meter) |
   916→   916→| Log storage (24h) | 0 credits (Free plan retention) |
   917→   917→
   918→   918→## When to use logs vs Blobs vs HTTP response
   919→   919→
   920→   920→| Use case | Best channel | Why |
   921→   921→|---|---|---|
   922→   922→| Large scraped data (>4 KB) | **Blobs** | No size limit, free, persistent |
   923→   923→| Small structured records (≤4 KB) | **Logs** | Easy to retrieve, parseable JSON Lines |
   924→   924→| Status / pointer / metadata | **HTTP response** | Returns immediately, no extra call needed |
   925→   925→| Audit trail / debug | **Logs** | Auto-timestamped, filterable by level |
   926→   926→| Real-time streaming | **Logs (`--follow`)** | Live tail mode |

   928→   928→## Combined scraping pattern (all 3 channels)
   929→   929→
   930→   930→```js
   931→   931→// Function does all 3:
   932→   932→export async function handler(event, context) {
   933→   933→  const targetUrl = event.queryStringParameters?.url;
   934→   934→  const r = await fetch(targetUrl);
   935→   935→  const body = await r.text();
   936→   936→
   937→   937→  // 1. WRITE TO BLOBS (large data, persistent, free)
   938→   938→  const { getStore } = await import('@netlify/blobs');
   939→   939→  const store = getStore('scrapes');
   940→   940→  const blobKey = `scrape-${Date.now()}`;
   941→   941→  await store.setJSON(blobKey, { url: targetUrl, body, ts: new Date().toISOString() });
   942→   942→  await store.setJSON('latest', { blob_key: blobKey });
   943→   943→
   944→   944→  // 2. LOG METADATA (small structured data, 24h retention, free)
   945→   945→  console.log(JSON.stringify({
   946→   946→    blob_key: blobKey,
   947→   947→    target_url: targetUrl,
   948→   948→    response_size: body.length,
   949→   949→    status: r.status,
   950→   950→    timestamp: new Date().toISOString(),
   951→   951→  }));
   952→   952→
   953→   953→  // 3. RETURN SMALL RESPONSE (pointer to blob, free)
   954→   954→  return {
   955→   955→    statusCode: 200,
   956→   956→    body: JSON.stringify({
   957→   957→      ok: true,
   958→   958→      blob_key: blobKey,  // Client fetches body via Blobs API
   959→   959→      size: body.length,
   960→   960→    }),
   961→   961→  };
   962→   962→}
   963→   963→```
   964→   964→
   965→   965→Client retrieval:
   966→   966→```bash
   967→   967→# Option A: Read the blob (large data, free)
   968→   968→curl -H "Authorization: Bearer $TOKEN" \
   969→   969→  "https://api.netlify.com/api/v1/blobs/$SITE_ID/site:scrapes/$BLOB_KEY"
   970→   970→
   971→   971→# Option B: Read the logs (small structured data, free, 24h)
   972→   972→netlify logs --json --since 1h --function <name>
   973→   973→```
